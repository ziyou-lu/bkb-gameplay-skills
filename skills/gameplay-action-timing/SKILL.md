# 输入响应与动作相位

本文件是从来源案例提炼的迁移流程，不是作者源码复刻，也未在目标游戏中执行。下面的验收项是实施后要做的检查，不是已经通过的测试。

## 触发条件

- 输入后首个可见响应太晚，但整段倍速又损失主体动作或收势重量。
- 动画堆积了不传达操作信息的表演，需要区分可删准备与玩法必要前后摇。

## 先确认的输入

输入接收、首个可见响应、关键姿态、实际命中/开火、恢复和取消事件；标出哪些准备段承担蓄力、敌人预警、冷却或反制窗口，哪些只是视觉表演。

## 分步机制

1. 先列出输入、准备、主体动作和收势的时间轴，分别记录可见响应、生效和恢复，不从起势画面推断伤害已生效。
2. 检查是否有不传达操作信息的额外表演。DP3HI8yjFUS 作者反思旧版帧数过多，旧版有额外持枪过程，新版保留伸臂射击/枪闪/回立姿；据此提出删减候选，不把作者反思当作测得延迟改善。
3. 当输入后的准备仅是冗余表演时，比较原版、只局部压缩准备段和整段加速，检查主体动作与收势是否保留重量；不直接给所有阶段同一倍速。
4. 若准备/蓄力本身就是玩法或敌人可读预兆，保留其规则，不沿用删除结论。需要改变真实攻击生效、取消、恢复或射击频率时，单列为玩法变更。
5. 重新核对关键姿态与真实时序；轮廓/smear 的表现问题转到形变入口，不用拉伸外形假装减少实际输入延迟。

## 适用限制

- DP3HI8yjFUS 没有实际帧数、时长或输入到开火测量；多项差异未单独消融，评论中的 gunspin 不是独立事实证据。
- DeuiO0UjRLM 三阶段各约三分之一和倍速是教学图，不是普遍比例；Diablo 3 的 1 FRAME 是作者标注，Mario 只是输入示意，均非本库独立测量，不设通用一帧目标。
- 作者正文已排除 wind-up 本身属于玩法的场景。没有命中盒、伤害生效、冷却或引擎实现证据，音频未核听；此处测时与规则保护是迁移建议。

## 验收

- [ ] 分别比较原版、只压缩冗余准备段与整体加速，独立记录输入、首个可见响应、真实生效和恢复时刻。
- [ ] 主体动作、关键姿态与收势仍可读，不以“看起来更利落”代替时序测量。
- [ ] 必要蓄力、敌人预警和反制窗口未被误删；纯表现优化不跳过冷却/前后摇或改变射击频率，预期玩法变化单列验收。
