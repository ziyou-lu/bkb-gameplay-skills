# 弹反窗口、成功确认与反击反馈

本文件是从来源案例提炼的迁移流程，不是作者源码复刻，也未在目标游戏中执行。下面的验收项是实施后要做的检查，不是已经通过的测试。

## 触发条件

- 已有或明确要设计弹反机制，但预备、失败、成功及后续反击机会的反馈混淆。
- 需要核对弹反显示与判定窗口，而不是普通近战增加一层火花。

## 先确认的输入

弹反输入、有效窗口与时钟、攻击可否被弹反、成功/失败事件、攻击者硬直/击退状态、反击条件，以及已有完美弹反或加伤规则。

## 分步机制

1. 先核对项目已有窗口和恢复条件。来源的宽容窗口是一个机制选择，不能因“加强手感”就扩宽判定；调整需明确列作规则变更。
2. 用预备姿势表达当前行为，但不要让姿势开始自动等于窗口已经生效。成功必须绑定真实判定结果，失败按项目已有结果处理。
3. 成功确认组合 [短停顿](../../gameplay-hitstop/SKILL.md) 与 [闪光/火花](../../gameplay-impact-visuals/SKILL.md)，避免普通格挡和成功弹反共用无法辨认的结果提示。
4. 对项目已有 stagger 显示攻击者暴露/失衡。DenLEa4xApp 第 6 步标题为 STAGGER，字幕描述击退攻击者并使其暴露；距离、硬直时长未核实，不能从碰撞截图补参数。
5. 只有真实规则允许反击奖励时才表达 COUNTER 或完美弹反层级。来源文字提到 bonus damage，不代表可以无授权给目标项目加伤；反击机会结束后及时退出提示。

## 适用限制

- 来源包含预备、宽容窗口、FREEZE + FLASH、火花、SOUND、STAGGER、COUNTER，但窗口和加伤数值未知，没有判定代码验证。
- 明亮 ting 叠厚重 clang 是字幕，不是已核听声音。
- 失败、取消、中断和恢复路径由项目规则定义；本页提供检查边界，不宣称来源已实现完整状态机。

## 验收

- [ ] 有效窗口开始/结束边界分别检查，显示成功与真实成功一致，不由特效碰撞自行判定。
- [ ] 成功、失败、不可弹反攻击和连续请求不误触发或重复奖励。
- [ ] 攻击者受影响状态、反击机会结束与双方控制恢复符合既有规则；未获准时不加击退/加伤。
- [ ] 关闭强闪光和镜头效果后仍能分辨成功与失败，后续攻击预警不被遮住。

## 组合而不复制

- [攻击预警](../../gameplay-attack-readability/SKILL.md)负责来招与可反制时机的可读性。
- [命中停顿](../../gameplay-hitstop/SKILL.md)、[冲击表现](../../gameplay-impact-visuals/SKILL.md)提供共享反馈。
- [近战编排](../../gameplay-melee-feedback/SKILL.md)处理普通命中，不再拥有弹反状态流程。
